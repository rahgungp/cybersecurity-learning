SECTION 01

Encryption vs Hashing vs Encoding vs MAC vs Digital Signature

Lima istilah ini sering tertukar padahal memiliki tujuan keamanan yang sepenuhnya berbeda:

MekanismeArahTujuanContoh
EncodingDua arah, TANPA kunciRepresentasi data (bukan keamanan)Base64, URL encoding
EncryptionDua arah, DENGAN kunciKerahasiaan (confidentiality)AES, RSA
HashingSatu arahIntegritas / verifikasiSHA-256, bcrypt
MACSatu arah + kunci rahasiaIntegritas + autentikasi pengirimHMAC-SHA256
Digital SignatureSatu arah + kunci privatIntegritas + autentikasi + non-repudiationRSA/ECDSA signature
Kesalahan Fatal Umum: Encoding (Base64) BUKAN enkripsi — tidak memerlukan kunci untuk dibalik dan tidak memberikan kerahasiaan sama sekali. Menyimpan password dalam Base64 "agar tidak plaintext" adalah ilusi keamanan.
SECTION 02

Symmetric vs Asymmetric Cryptography

🔑 SYMMETRIC (AES)

Satu kunci sama untuk enkripsi & dekripsi

  • Sangat cepat
  • Cocok data besar
  • Masalah: distribusi kunci
  • AES-256 = standar industri

🔐🔓 ASYMMETRIC (RSA/ECC)

Pasangan kunci publik-privat

  • Lebih lambat
  • Memecahkan masalah distribusi kunci
  • ECC: keamanan setara RSA, kunci lebih pendek
  • Dasar PKI & digital signature

⚡ HYBRID (praktik nyata)

Kombinasi keduanya — dipakai TLS

  • Asymmetric untuk tukar kunci sesi
  • Symmetric (AES) untuk data aktual
  • Terbaik dari dua dunia
SECTION 03

PKI & TLS Handshake

Public Key Infrastructure (PKI) adalah sistem yang mengikat identitas dengan kunci publik melalui sertifikat digital yang diterbitkan Certificate Authority (CA) tepercaya. TLS memanfaatkan PKI untuk membangun koneksi terenkripsi (HTTPS):

CLIENT HELLOClient kirim cipher suite yang didukung
TLS version, random number
→
SERVER HELLO + CERTServer kirim sertifikat & kunci publik
Ditandatangani CA tepercaya
→
VERIFY CERTClient verifikasi rantai kepercayaan
Cek CA, expiry, hostname
→
KEY EXCHANGESepakati session key (symmetric)
Diamankan via asymmetric crypto
→
ENCRYPTED SESSIONData dikirim via AES
HTTPS aktif — gembok muncul

Jika salah satu langkah verifikasi gagal (mis. sertifikat kedaluwarsa atau CA tidak dikenal), browser menampilkan peringatan — jangan pernah diabaikan begitu saja, karena ini bisa jadi indikasi serangan man-in-the-middle.

SECTION 04

Encryption at Rest vs In Transit

DATA IN TRANSIT
TLS/HTTPS, VPN — melindungi data saat berpindah
＋
DATA AT REST
Disk encryption, database encryption — melindungi data saat tersimpan
＝
DEFENSE IN DEPTH UNTUK DATA

Kedua jenis perlindungan diperlukan — mengenkripsi data in transit saja tidak melindungi database yang dicuri langsung dari server; mengenkripsi data at rest saja tidak melindungi data yang disadap saat dikirim melalui jaringan tidak aman.

SECTION 06

Real-World Case Studies

CASE 01 · IMPLEMENTATION FLAW, BUKAN ALGORITMA Heartbleed (CVE-2014-0160)

Heartbleed adalah kerentanan pada implementasi OpenSSL (bukan pada algoritma TLS itu sendiri) yang memungkinkan penyerang membaca hingga 64KB memori server per request — termasuk kunci privat TLS, password, dan session token — tanpa meninggalkan jejak di log normal. Ditemukan April 2014, memengaruhi diperkirakan 17% server HTTPS di internet saat itu.

ROOT CAUSE

Bug pada implementasi fitur "heartbeat" OpenSSL — kegagalan validasi panjang buffer

DAMPAK

Potensi kebocoran kunci privat TLS, memungkinkan dekripsi traffic yang direkam sebelumnya

REMEDIASI

Patch OpenSSL + reissue seluruh sertifikat TLS + rotasi seluruh kredensial

Lesson Learned: Algoritma kriptografi yang matematis kuat tidak berguna jika implementasinya memiliki bug — code review dan patch management tetap krusial untuk komponen kriptografi.
CASE 02 · WRONG PRIMITIVE (ENCRYPTION vs HASHING) Adobe Password Breach (2013)

Pada 2013, Adobe mengalami kebocoran data yang memengaruhi ~153 juta akun. Alih-alih menggunakan hashing khusus password, Adobe menyimpan password dalam bentuk terenkripsi (encrypted) menggunakan kunci simetris yang sama untuk semua pengguna, dengan password hint yang disimpan dalam plaintext di sebelahnya. Karena enkripsi bersifat deterministik (password sama menghasilkan ciphertext sama) dan hint plaintext tersedia, peneliti keamanan berhasil mengidentifikasi ribuan password hanya dengan menganalisis pola ciphertext dan hint-nya.

ROOT CAUSE

Penggunaan encryption (reversible, deterministik) alih-alih hashing khusus password (irreversible, unik per user via salt)

FAKTOR PEMBERAT

Password hint disimpan plaintext, mempermudah analisis pola ciphertext

LESSON

Ini adalah contoh klasik kesalahan memilih primitif kriptografi yang salah untuk tujuan yang salah

Lesson Learned: Password HARUS di-hash dengan algoritma khusus (bcrypt/Argon2) dengan salt unik per pengguna — bukan dienkripsi, apa pun alasannya.

🔍 Think Like a Security Analyst

Skenario: Tim developer UND membangun fitur baru pada SIAKAD: mahasiswa dapat mengunggah dokumen KTP untuk verifikasi. Developer menyimpan file KTP di server tanpa enkripsi ("toh sudah di folder khusus admin"), dan menyimpan password SIAKAD menggunakan MD5 tanpa salt ("MD5 kan sudah standar hashing").

💡 Pertanyaan Analisis — Cryptography UND

1. Apa yang salah dengan pendekatan "folder khusus admin" untuk melindungi file KTP?
Ini mengandalkan access control saja (Module 04) tanpa encryption at rest — jika access control gagal (misconfiguration, privilege escalation, atau server dicuri fisik), data KTP langsung terekspos. Data sensitif seperti KTP idealnya dienkripsi at rest sebagai defense in depth, bukan hanya diandalkan pada satu lapisan kontrol.
2. Mengapa MD5 tanpa salt adalah pilihan yang salah untuk hashing password, meski "MD5 adalah algoritma hashing"?
MD5 dirancang cepat (untuk checksums, bukan password) dan rentan brute-force serta rainbow table attack tanpa salt. MD5 juga memiliki kerentanan collision yang terdokumentasi. Password harus menggunakan algoritma yang sengaja lambat (bcrypt/Argon2) dengan salt unik per pengguna.
3. Bagaimana kasus Adobe 2013 relevan untuk mengevaluasi risiko pendekatan developer UND ini?
Baik Adobe (memakai encryption untuk password) maupun UND (memakai MD5 tanpa salt) menunjukkan pola yang sama: memilih primitif kriptografi yang salah untuk konteksnya. Keduanya memberi ilusi keamanan ("sudah dienkripsi/di-hash") tanpa perlindungan nyata terhadap serangan realistis.
4. Susun rekomendasi perbaikan untuk kedua masalah ini.
File KTP: enkripsi at rest menggunakan AES-256, kunci dikelola terpisah dari server aplikasi (key management terpusat), akses tetap dibatasi RBAC (Module 04). Password: migrasi ke bcrypt/Argon2 dengan salt unik, dengan strategi migrasi bertahap (re-hash saat user login berikutnya) agar tidak perlu reset password massal.

🏁 Key Takeaways

MODULE 05 — CORE INSIGHTS

  • Encoding, encryption, hashing, MAC, dan digital signature memiliki tujuan keamanan yang berbeda — memilih primitif yang salah adalah kesalahan fatal (lih. Adobe 2013).
  • Symmetric cryptography cepat namun sulit distribusi kunci; asymmetric memecahkan masalah itu namun lebih lambat — TLS menggunakan hybrid dari keduanya.
  • PKI dan rantai kepercayaan sertifikat adalah fondasi HTTPS — peringatan sertifikat tidak boleh diabaikan.
  • Data memerlukan perlindungan encryption at rest DAN in transit — keduanya, bukan salah satu.
  • Kelemahan kriptografi di dunia nyata (Heartbleed) lebih sering berasal dari kesalahan implementasi daripada kelemahan algoritma matematis.
  • Password wajib di-hash dengan algoritma khusus (bcrypt/Argon2 + salt), tidak pernah dienkripsi atau di-hash dengan algoritma umum seperti MD5/SHA-256 polos.

📖 Glossary

Symmetric Cryptography

Skema enkripsi yang menggunakan satu kunci sama untuk enkripsi dan dekripsi (mis. AES).

Asymmetric Cryptography

Skema enkripsi menggunakan pasangan kunci publik-privat (mis. RSA, ECC).

PKI

Public Key Infrastructure — sistem yang mengikat identitas dengan kunci publik melalui sertifikat digital.

Certificate Authority (CA)

Entitas tepercaya yang menerbitkan dan menandatangani sertifikat digital.

MAC

Message Authentication Code — menggabungkan hashing dengan kunci rahasia untuk verifikasi integritas dan keaslian pengirim.

Digital Signature

Tanda tangan digital menggunakan kunci privat untuk membuktikan keaslian dan integritas pesan, serta non-repudiation.

Encryption at Rest

Enkripsi data yang tersimpan pada media penyimpanan (disk, database).

Encryption in Transit

Enkripsi data yang sedang berpindah melalui jaringan (mis. TLS).
