SECTION 02

Vulnerability vs Exploit vs Risk — Revisited

Module 02 memperkenalkan konsep ini; berikut ditegaskan kembali dalam konteks operasional vulnerability management:

IstilahDefinisi OperasionalContoh
VulnerabilityKelemahan yang terdaftar dan diberi identifier (CVE)CVE-2021-44228
ExploitBukti/alat yang mengonfirmasi vulnerability dapat dimanfaatkanPoC exploit code, Metasploit module
RiskKombinasi vulnerability + exposure + kekritisan asset dalam konteks organisasi spesifik"CVE ini HIGH risk untuk kami karena internet-facing"
SECTION 03

CVSS — Cara Kerja & Keterbatasan

CVSS (Common Vulnerability Scoring System) menghasilkan skor 0–10 berdasarkan metrik seperti Attack Vector, Attack Complexity, Privileges Required, dan Impact. Namun CVSS Base Score TIDAK memperhitungkan konteks organisasi — apakah sistem benar-benar terekspos, apakah exploit tersedia secara aktif di alam liar.

Keterbatasan Kunci: Dua organisasi dapat memiliki CVE yang sama dengan CVSS 9.8, namun risiko aktual sangat berbeda tergantung exposure dan kekritisan sistem masing-masing (lih. contoh Server A vs B, Module 02).

SECTION 05

Real-World Case Studies

CASE 01 · KECEPATAN EKSPLOITASI GLOBALLog4Shell — CVE-2021-44228

Log4Shell adalah kerentanan kritis (CVSS 10.0) pada library logging Java Log4j yang digunakan luas di jutaan aplikasi enterprise di seluruh dunia. Dalam hitungan jam setelah diumumkan Desember 2021, eksploitasi aktif terdeteksi secara massal karena kemudahan eksploitasi (attacker hanya perlu mengirim string tertentu) dan penyebaran library yang sangat luas — banyak organisasi bahkan tidak sadar mereka menggunakan Log4j karena ia adalah dependency tersembunyi dari komponen lain.

TANTANGAN UTAMA

Asset Discovery gagal — organisasi tidak tahu mereka menggunakan Log4j (dependency transitif)

KECEPATAN

Eksploitasi massal dalam hitungan jam, jauh lebih cepat dari siklus patch normal

CISA KEV

Segera masuk katalog KEV — prioritas remediasi maksimal di seluruh dunia

Lesson Learned: Asset Discovery yang lengkap (termasuk dependency pihak ketiga tersembunyi) adalah tahap paling fundamental — kamu tidak dapat menambal kerentanan pada komponen yang tidak kamu ketahui kamu gunakan.
CASE 02 · MASS EXPLOITATION SETELAH PATCH TERSEDIAProxyShell — Microsoft Exchange (2021)

Rangkaian kerentanan ProxyShell pada Microsoft Exchange Server dieksploitasi secara massal oleh berbagai kelompok ransomware beberapa bulan setelah Microsoft merilis patch — organisasi yang belum menambal menjadi target mudah bagi scanning otomatis penyerang yang mencari server Exchange rentan di seluruh internet.

POLA

Patch tersedia namun banyak organisasi terlambat menerapkan (lih. WannaCry, Module 01)

DAMPAK

Menjadi pintu masuk favorit berbagai kelompok ransomware selama berbulan-bulan

Lesson Learned: Pola "patch tersedia tapi terlambat diterapkan" berulang terus dalam sejarah insiden besar — verification (memastikan patch benar-benar diterapkan) sama pentingnya dengan remediation itu sendiri.

🔍 Think Like a Security Analyst

Skenario: Scanning terhadap server UND menemukan 47 kerentanan: 5 Critical (CVSS 9+), 12 High, 20 Medium, 10 Low. Tim IT hanya punya waktu 1 minggu sebelum jadwal maintenance berikutnya.

💡 Pertanyaan Analisis — Vulnerability Management UND

1. Apakah cukup langsung menambal 5 CVE Critical terlebih dahulu tanpa analisis tambahan?
Belum cukup — perlu diperiksa juga apakah CVE tersebut ada di CISA KEV (bukti eksploitasi aktif) dan bagaimana exposure-nya (internet-facing atau internal). Bisa jadi ada CVE High yang justru lebih mendesak karena sudah dieksploitasi aktif, dibanding CVE Critical yang exposure-nya sangat terbatas.
2. Bagaimana kamu memvalidasi apakah hasil scan bukan false positive sebelum menambal?
Verifikasi manual: cek versi software aktual pada sistem, konfirmasi apakah patch yang relevan sudah/belum terpasang, dan jika memungkinkan uji exploit di lingkungan staging (bukan produksi) untuk memastikan kerentanan benar-benar dapat dieksploitasi pada konfigurasi spesifik UND.
3. Bagaimana kasus Log4Shell mengingatkan UND untuk memeriksa dependency, bukan hanya software utama?
UND perlu memastikan asset inventory (Module 02) mencakup dependency/library pihak ketiga pada aplikasi mereka (SIAKAD, LMS), bukan hanya OS dan aplikasi utama — banyak kerentanan kritis bersembunyi pada komponen "tak terlihat" seperti Log4j.

🏁 Key Takeaways

MODULE 11 — CORE INSIGHTS

  • Siklus vulnerability management: Asset Discovery → Scanning → Validation → Risk Rating → Prioritization → Remediation → Verification → Reporting.
  • Vulnerability adalah kelemahan terdaftar, exploit adalah bukti eksploitasi, risk adalah kombinasi keduanya dengan konteks organisasi.
  • CVSS Base Score tidak memperhitungkan exposure aktual — prioritas remediasi idealnya berbasis risiko, bukan CVSS semata.
  • False positive membuang waktu remediasi; false negative meninggalkan risiko nyata tidak tertangani — validasi tetap penting.
  • Asset discovery yang tidak lengkap (dependency tersembunyi seperti Log4j) adalah kegagalan fundamental vulnerability management.
  • Verification memastikan remediasi benar-benar berhasil diterapkan, bukan hanya diasumsikan (lih. ProxyShell).

📖 Glossary

False Positive

Hasil scan yang melaporkan kerentanan padahal sebenarnya tidak ada/tidak dapat dieksploitasi.

False Negative

Kerentanan nyata yang luput tidak terdeteksi oleh proses scanning.

CVSS

Common Vulnerability Scoring System — sistem penilaian keparahan kerentanan skala 0-10.

Patch Management

Proses terstruktur menerapkan pembaruan keamanan (patch) pada sistem secara tepat waktu.

Dependency

Komponen/library pihak ketiga yang digunakan oleh sebuah aplikasi, sering tersembunyi dari asset inventory sederhana.
