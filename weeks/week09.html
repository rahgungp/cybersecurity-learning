SECTION 01

Secure SDLC — Shift-Left Security

Secure Software Development Life Cycle (SDLC) mengintegrasikan pertimbangan keamanan pada SETIAP fase pengembangan — bukan hanya sebagai pengecekan terakhir sebelum rilis. Prinsip "shift-left" berarti menemukan dan memperbaiki masalah keamanan sedini mungkin, karena biaya perbaikan meningkat drastis semakin jauh masalah ditemukan dari fase desain.

SECTION 03

Injection, XSS, CSRF, SSRF — Membedakan Mekanisme

💉 INJECTION

Input diproses SERVER sebagai perintah

  • SQL injection
  • Command injection

🖼 XSS

Skrip dieksekusi di BROWSER korban

  • Stored / Reflected / DOM-based

🎭 CSRF

BROWSER korban dipaksa kirim request

  • Korban tidak sadar mengirim aksi

🔄 SSRF

SERVER dipaksa buat request tidak sah

  • Target: internal network/cloud metadata
⚠️ Perbedaan kunci: Injection & SSRF mengeksploitasi server; XSS & CSRF mengeksploitasi browser korban (client-side) — meski sama-sama berawal dari input yang tidak divalidasi dengan benar.

SECTION 05

Real-World Case Studies

CASE 01 · SSRF + CLOUD MISCONFIGURATIONCapital One Data Breach (2019)

Penyerang mengeksploitasi kerentanan Server-Side Request Forgery (SSRF) pada Web Application Firewall yang salah dikonfigurasi milik Capital One yang berjalan di AWS. Melalui SSRF, penyerang memaksa server membuat request ke endpoint metadata AWS internal untuk mencuri kredensial sementara (IAM role), yang kemudian digunakan untuk mengakses dan mengunduh data lebih dari 100 juta pelanggan dari storage S3.

TEKNIK

SSRF → curi kredensial IAM dari metadata service → akses S3 bucket

ROOT CAUSE

WAF misconfigured memiliki hak akses IAM berlebihan (pelanggaran least privilege, lih. Module 04)

IMPACT

~100 juta data pelanggan, denda regulator $80 juta

Lesson Learned: SSRF menjadi berbahaya secara eksponensial pada arsitektur cloud karena metadata service internal dapat menjadi jalur pencurian kredensial — kombinasi OWASP Top 10 dan cloud security (Module 03).
CASE 02 · INJECTION PADA SKALA GLOBALEquifax Breach — CVE-2017-5638

Kebocoran data Equifax 2017 (~147 juta korban) bermula dari kerentanan remote code execution pada framework Apache Struts (CVE-2017-5638) — sebuah kelas kerentanan injection di mana header HTTP yang dibuat khusus dapat menjalankan perintah pada server. Patch untuk CVE ini telah tersedia dua bulan sebelum insiden terjadi.

KATEGORI OWASP

Injection (RCE via header manipulation) + Vulnerable Components

ROOT CAUSE

Kegagalan patch management (lih. Module 03) pada komponen framework pihak ketiga

Lesson Learned: Vulnerable & outdated components adalah kategori OWASP yang sering diabaikan — komponen pihak ketiga memerlukan patch management sama ketatnya dengan kode sendiri.

🔍 Think Like a Security Analyst

Skenario: Portal pendaftaran online UND memiliki fitur "cek status pendaftaran" yang menerima parameter ?id= pada URL tanpa validasi, dan halaman error menampilkan detail query SQL lengkap ketika terjadi kesalahan input.

💡 Pertanyaan Analisis — Web Security UND

1. Kategori OWASP Top 10 apa saja yang berpotensi terjadi pada skenario ini?
Broken Access Control (parameter id tanpa verifikasi kepemilikan), potensi Injection (jika parameter langsung dimasukkan ke query SQL tanpa parameterized query), dan Security Misconfiguration (error message menampilkan detail teknis/query SQL yang seharusnya disembunyikan dari pengguna).
2. Mengapa menampilkan detail query SQL pada halaman error berbahaya, meski terlihat "hanya untuk debugging"?
Ini memberi penyerang informasi berharga tentang struktur database (nama tabel, kolom) yang mempermudah merancang serangan injection lebih lanjut — prinsip defensif adalah menampilkan pesan error generik ke pengguna sambil mencatat detail teknis hanya di log server (Module 12).
3. Rekomendasikan perbaikan untuk kedua masalah ini, dihubungkan dengan prinsip Secure SDLC.
Access control: verifikasi kepemilikan data di server sebelum mengembalikan hasil (bukan mengandalkan parameter URL semata). Error handling: gunakan generic error message untuk pengguna, log detail teknis secara terpisah. Idealnya kedua isu ini seharusnya tertangkap saat fase Test (DAST/code review) sebelum Production — prinsip shift-left.

🏁 Key Takeaways

MODULE 09 — CORE INSIGHTS

  • Secure SDLC menerapkan prinsip shift-left — menemukan masalah keamanan sedini mungkin jauh lebih murah dibanding setelah production.
  • OWASP Top 10 adalah acuan standar industri untuk memprioritaskan risiko aplikasi web.
  • Injection dan SSRF mengeksploitasi server; XSS dan CSRF mengeksploitasi browser korban.
  • Broken Access Control terjadi ketika aplikasi tidak memverifikasi kepemilikan resource di sisi server.
  • Vulnerable components (framework/library pihak ketiga) memerlukan patch management yang sama ketatnya dengan kode sendiri (lih. Equifax).
  • SSRF menjadi sangat berbahaya di arsitektur cloud karena dapat mencuri kredensial dari metadata service (lih. Capital One).

📖 Glossary

Secure SDLC

Integrasi pertimbangan keamanan pada setiap fase pengembangan software.

Broken Access Control

Kegagalan aplikasi memverifikasi hak akses pengguna terhadap resource yang diminta.

SSRF

Server-Side Request Forgery — memaksa server membuat request ke tujuan yang tidak sah.

XSS

Cross-Site Scripting — eksekusi skrip berbahaya di browser korban akibat input tidak di-escape.

CSRF

Cross-Site Request Forgery — memaksa browser korban mengirim request tanpa sepengetahuannya.

Security Misconfiguration

Kesalahan konfigurasi seperti fitur default aktif atau pesan error yang membocorkan informasi teknis.
